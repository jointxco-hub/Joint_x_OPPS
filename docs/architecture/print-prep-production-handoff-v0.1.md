# Print Prep Production Handoff v0.1

Status: draft contract for implementation  
Scope: OPPS -> Print Prep -> OPPS  
Base principle: OPPS owns production truth; Print Prep is an execution client.

## 1. Why this exists

X LAB orders now enter OPPS with frozen production snapshots. Print Prep already has working local prep, DTF run, recovery, supplier, preflight, export, revision and send-to-supplier flows. This contract connects those systems without making CorelDRAW, Affinity, CSL libraries, or a local JSON snapshot the system of record.

The contract is intentionally software-agnostic. A Corel or Affinity adapter may consume it, but neither application-specific identifier is canonical production identity.

## 2. Source-of-truth rules

1. Existing order production truth remains the frozen OPPS order-line/component snapshot.
2. The handoff must read frozen order production fields, not silently re-follow current product configuration.
3. Existing OPPS production-readiness rules remain authoritative before a job can be released.
4. Print Prep may add execution metadata and results, but it must not rewrite the frozen sales/configuration snapshot.
5. Local Print Prep recovery remains a fallback, not the authoritative store.
6. Offline work must be replayable through idempotent result events when connectivity returns.

## 3. Canonical identities

The first implementation should carry the narrowest existing identifiers that let OPPS reconcile a result:

- tenant_id
- order_id
- line_id
- order_line_component_snapshot_id
- client_product_id when present
- artwork_revision_ids from the frozen snapshot
- handoff_id generated by OPPS
- contract_version

Do not use Corel StaticID, symbol name, page name, filename, or local library path as canonical identity. They may be retained as adapter/recovery metadata.

  },
  "production_component": {
    "snapshot_id": "uuid",

### Required fields for v0.1

The first implementation should fail closed if any of these are missing:

- contract_version
- handoff_id
- tenant_id
- order.id
- order.line_id
- production_component.snapshot_id
- production_component.production_method
- production_component.placement
- artwork.revision_ids
- production.quantity

Sizing may remain unset when the production component legitimately requires operator sizing. Print Prep must then show that as an operator decision, not invent a value.

### Sizing modes

The contract supports three operator-safe sizing modes:

- `width` — width is authoritative; height follows artwork aspect ratio.
- `height` — height is authoritative; width follows artwork aspect ratio. This is important for tall/back prints where a width-first rule could exceed the blank.
- `custom` — explicit width + height. `lock_aspect_ratio=true` keeps artwork proportional; unlocking proportions must be an explicit operator choice.

OPPS/X LAB should eventually save this sizing object as part of the production configuration before the order is frozen. Preset names (Small/Standard/Large) are UI conveniences only; the frozen production contract carries the resolved sizing rule/dimensions. Until OPPS/X LAB sizing persistence is implemented, Print Prep remains allowed to make the sizing decision locally and the handoff sends `sizing: null`.

## 5. Existing OPPS fields mapped into the contract

The current frozen snapshot model already contains the production-critical fields we should reuse:

- component_type
- production_method
- placement
- production_colour
- specification
- production_instructions
- quantity_per_unit
- artwork_revision_ids
- resolved_inventory_variant_id
- inventory_product_id
- label

The existing production-readiness implementation already blocks missing production_method, missing placement, missing required artwork, unresolved stock variants, invalid artwork revisions, missing approvals, and unresolved price state.

The handoff must consume that readiness outcome rather than reimplementing a second readiness engine in Print Prep.

## 6. Print Prep operator state

When the payload is accepted, Print Prep should populate the compact operator UI instead of asking staff to retype:

- client/order identity
- artwork identity
- production method
- placement
- sizing mode/dimensions if supplied
- quantity

The existing three-stage operator UI remains:

1. Prep
2. DTF Run
3. Output

Local identity/library controls remain fallback/recovery tools. For an OPPS-fed job they should be secondary and normally collapsed.

## 8. Event types for the first slice

Keep v0.1 narrow:

- production_handoff_opened
- production_artwork_prepared
- production_run_built
- production_run_exported
- production_run_sent_to_supplier

Later events can cover received, printed, cut, QC, packed, failed, or merchant acknowledgements.

## 9. Offline/outbox rule

Print Prep should eventually keep result events locally when OPPS cannot be reached.

Minimum future outbox record:

~~~json
{
  "event_id": "uuid",
  "handoff_id": "uuid",
  "payload": {},
  "created_at": "ISO-8601",
  "sync_state": "pending",
  "attempt_count": 0,
  "last_error": null
}
~~~

When connectivity returns:

1. replay pending events in created order;
2. OPPS de-duplicates by event_id;
3. successful events become synced;
4. rejected/conflicting events remain visible for operator review.

The local outbox is a transport/recovery layer, not canonical production history.

## 10. Security boundary

- The handoff is an internal OPPS production contract.
- It must be tenant-scoped.
- Asset access should use opaque references or short-lived authorized URLs rather than exposing unrestricted storage paths.
- Do not expose supplier costs, trade secrets, internal margins, or unrelated tenant data.
- Print Prep should only receive what the operator needs for the specific production item/run.

## 11. First implementation slice

Do not start with full Bridge/offline automation.

### Slice A — read-only OPPS handoff

Add an OPPS action on a production-capable order line:

**Open / Send to Print Prep**

It produces the v0.1 payload and shows a reviewable handoff state.

### Slice B — Print Prep import

Print Prep accepts the payload and populates:

- order/client
- artwork references
- production method
- placement
- width
- quantity

No automatic production mutation in OPPS yet.

### Slice C — result acknowledgement

After Build / Export, Print Prep returns only:

- run id
- revision
- status
- piece/master count
- sheet dimensions/utilization
- supplier
- output filename/reference

OPPS records that as production execution history.

### Slice D — offline outbox

Only after the connected path is stable.

## 12. UI placement in OPPS

The first OPPS UI should live with the order's production line, not as a new top-level system.

Suggested operator surface:

- readiness badge
- production method / placement
- artwork count/status
- **Open in Print Prep**
- latest Print Prep status
- latest run / revision
- supplier + sheet usage when available

This keeps production attached to the order and avoids creating a second job-management model.

## 13. Non-goals for v0.1

- no mockup-prep implementation yet
- no SVG garment-template workflow yet
- no automatic merchant/Bridge dispatch
- no full offline OPPS application work
- no Corel-only identifiers in canonical OPPS tables
- no replacement of current local CSL/JSON recovery
- no rewrite of order-line production-readiness rules

## 14. Implementation order

1. Land the current X LAB order-creation hotfix.
2. Add a server-side OPPS handoff reader over frozen snapshots/readiness.
3. Add the order-line production UI action.
4. Add Print Prep payload import.
5. Add result event ingestion/history.
6. Add offline outbox.
7. Then continue mockup/SVG production workflow.

This preserves the current hotfix lane while making the production contract ready to wire in as soon as the order path is stable.
