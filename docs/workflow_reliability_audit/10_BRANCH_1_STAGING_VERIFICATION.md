# Branch 1 Staging Verification — Invoice Item Reliability

## Verdict

The critical guarantee was proven in disposable local database and real browser conditions:

> A failed invoice load or failed invoice update did not erase previously saved invoice line items.

Branch: `fix/invoice-item-reliability`

## Rollback rehearsal

The first disposable database rehearsed coordinated function rollback:

```text
invoices_before=3, items_before=5
REVOKE
DROP FUNCTION
invoices_after=3, items_after=5, function_removed=true
tenant_a_readable_invoices=2
```

No table, invoice, item, or activity row was removed. Existing invoices remained readable through RLS. The safe rollback remains: revert the client first, then revoke/drop only the six-argument function.

## Defects found and changes made during verification

1. **Search-path and default-grant hardening**
   - Changed function search path from `public` to `pg_catalog, public`.
   - Explicitly revoked `service_role` in addition to `public` and `anon` because the local Supabase image's default privileges otherwise granted it.
2. **False item-history change caused by JSON key ordering**
   - PostgreSQL `jsonb` canonicalized object key order, while the client compared snapshots with raw `JSON.stringify`.
   - Identical snapshots were incorrectly treated as changes, blocking a later save.
   - Added canonical recursive object-key comparison plus regression coverage.
3. **Technical constraint feedback**
   - Mapped common PostgreSQL validation/FK/not-null/format codes to actionable invoice messages.
4. **Missing load/retry notifications**
   - Added explicit Sonner feedback for detail-load failure and successful retry.
5. **Reusable verification harness**
   - Added synthetic fixture, integration SQL, dependency-free Chrome workflow, and screenshot evidence.

## Known limitation review

### Client item-template synchronization

Template synchronization occurs before the core invoice RPC. It can throw before the invoice transaction begins, so it cannot partially delete invoice items. However, a template insert/update can commit and the later invoice RPC can fail, leaving the template changed without a matching invoice save. This is an auxiliary consistency risk.

Recommendation: move template synchronization into a separately designed transactional workflow or make it explicitly post-save/best-effort in a follow-up. It does not invalidate the proven header/item atomicity, but it should be resolved before claiming the whole template-plus-invoice workflow is atomic.

### Item-version history

Version history is written after the core RPC. Its error is caught and safely diagnosed, so a committed invoice is not falsely reported as unsaved. The remaining risk is missing audit history after an otherwise successful invoice save.

The key-order defect that incorrectly blocked repeat saves was fixed in this verification. Moving version insertion into the RPC would provide stronger audit completeness and is recommended as a follow-up, but is not required to prevent invoice-item loss.
